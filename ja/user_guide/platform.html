プラットフォーム¶

クラス構成¶

以下は、mainファイルにおける典型的なコードです：

runner = SequentialRunner(
    settings=setting_dict_or_json,
    prng=random.Random(seed),
    logger=MarketStepPrintLogger(),
)
runner.main()

このコードが示すように、シミュレーションはランナー（この場合は SequentialRunner）によって完全に制御されます。Runner は通常、設定の辞書、疑似乱数生成器、ロガーを受け取ります。

以下の図はクラス構成を示しています。

mainは通常、ロガーを保持し、ランナーを生成します。ランナーとしては、Parallel RunnerまたはSequential Runnerを利用できます。ランナーは、シミュレーターと、市場、エージェント、イベントなどのその他のコンポーネントを生成します。その後、ランナーはすべてのコンポーネントとシミュレーターを自身のルールに従って制御します。一方、シミュレーターは、ランナーがシミュレーションを制御する手順を定義するためのAPIインターフェースを提供します。さらに、シミュレーターとそのコンポーネントはログを生成し、ロガーに送ります。

このプラットフォームの重要なコンセプトは、より複雑なシミュレーター制御を実現するために、ランナーを差し替えられるようにしていることです。

並列ランナー¶

pams.runners.MultiThreadAgentParallelRunner と pams.runners.MultiProcessAgentParallelRunner は、各ステップにおける通常エージェント（高頻度エージェント以外）の注文の提出を並列化する実験的なランナーです。これらは pams.runners.SequentialRunner をそのまま置き換えて使うことができ、同じ設定と同じシードであれば、シミュレーション結果は pams.runners.SequentialRunner と同じになります。ワーカー数は設定ファイルの simulation.numParallel で設定できますが、各ステップで並列化できるエージェント数はセッションの maxNormalOrders によって制限されます。

runner = MultiThreadAgentParallelRunner(
    settings=setting_dict_or_json,
    prng=random.Random(seed),
    logger=MarketStepPrintLogger(),
)
runner.main()

PythonのGILのため、pams.runners.MultiThreadAgentParallelRunner が効果を発揮するのは、エージェントの注文の提出がI/O（外部のモデルやサービスなど）を待つ場合に限られます。pams.runners.MultiProcessAgentParallelRunner はステップごとにシミュレーション全体をワーカープロセスにコピーするため、はるかに低速になります。また、ユーザー定義のクラスはpickle可能であり、かつワーカープロセスからインポート可能である必要があります。ワーカープロセスの開始方式（spawn、fork、forkserver）は設定ファイルの simulation.startMethod で設定できます。詳細とコピーのコストについては 並列ランナー を参照してください。

ワーカーのカスタマイズ¶

並列ランナーのサブクラスは、以下のメンバーをオーバーライドすることでワーカーをカスタマイズできます。

  • default_start_method （クラス属性、プロセスランナーのみ）：simulation.startMethod が設定されていない場合に使われる開始方式です。デフォルトの None はプラットフォームのデフォルトを意味します。実際に使われる開始方式は start_method に格納されます。

  • _get_mp_context() （プロセスランナーのみ）：ワーカープロセスの multiprocessing コンテキストです。デフォルトは multiprocessing.get_context(self.start_method) です。

  • _get_worker_initializer() と _get_worker_initargs()：各ワーカー（スレッドまたはプロセス）がタスクを実行する前に一度だけ呼び出される関数と、その引数です。デフォルトでは何も呼び出されません。プロセスランナーでは、この関数はワーカープロセスがインポートできるモジュールのトップレベルで定義する必要があり、引数はpickle可能でなければなりません。あるワーカーでこの関数が SystemExit などの BaseException を含む何らかの例外を送出すると、そのワーカー上のタスクはその例外を原因とする RuntimeError を送出し、シミュレーションは失敗します。プロセスランナーでは、この RuntimeError の __cause__ は例外そのものではなく、ワーカーのトレースバックのテキストです。

  • _create_executor()：タスクを実行する concurrent.futures.Executor です。デフォルトでは、上記のメンバーを用いて、numParallel 個のワーカーを持つ _parallel_pool_provider （concurrent.futures.ThreadPoolExecutor または concurrent.futures.ProcessPoolExecutor）を作成します。

  • _split_agents_into_chunks(agents)：同時に注文の提出を求められるエージェントをタスクに分ける方法です。1つのタスクのエージェントには、同じワーカー上で1つずつ注文の提出を求めます。スレッドランナーはエージェントごとに1つのタスクを作成し、プロセスランナーは、各タスクでシミュレーション全体がコピーされるため、連続するエージェントからなるタスクを最大 numParallel 個作成します。結果が pams.runners.SequentialRunner と同じになるよう、タスクはすべてのエージェントを与えられた順序のまま含む必要があります。そうでない場合、シミュレーションは ValueError で失敗します。

例えば、以下のランナーはワーカープロセスを spawn で起動し、各ワーカープロセスでモデルを一度だけ読み込みます。モデルがタスクごとにコピーされないよう、エージェントはモデルを自身の属性として保持する代わりに、submit_orders 内で my_runner.MODEL を使います。

# my_runner.py, which the worker processes can import
from typing import Any, Callable, Optional, Tuple

from pams.runners import MultiProcessAgentParallelRunner

MODEL = None


def load_model(path: str) -> None:
    global MODEL
    MODEL = ...  # load the model from path


class MyRunner(MultiProcessAgentParallelRunner):
    default_start_method = "spawn"

    def _get_worker_initializer(self) -> Optional[Callable[..., Any]]:
        return load_model

    def _get_worker_initargs(self) -> Tuple[Any, ...]:
        return ("model.bin",)

JAX/Flax ランナー¶

pams.runners.JaxAgentParallelRunner は、submit_orders で JAX （例えば Flax のニューラルネットワークのモデル）を使うエージェントのための、実験的な pams.runners.MultiProcessAgentParallelRunner です。JAXはpamsの依存関係ではないため、別途インストールしてください（例えば pip install pams jax flax。GPUについては JAXのインストールガイド を参照してください）。pamsがインストール済みでも、コマンドにpamsを含めてください。そうすると、pipはpamsが必要とするNumPyで動作するバージョンのJAXとFlaxを選びます。例えば、Python 3.12以前ではpamsはNumPy 1.xを必要とし、これをサポートするJAXとFlaxの最後のバージョンは0.7.1と0.12.0です。import pams ではJAXはインポートされず、JAXがない状態でこのランナーを作成すると ImportError が送出されます。

  • JAXが独自のスレッドを実行し始めると fork は安全ではなくなるため、ワーカープロセスはデフォルトで spawn によって起動されます（default_start_method = "spawn"）。forkされたワーカープロセスは、それらのスレッドのいずれかが保持していたロックでデッドロックする可能性があります。

  • 各ワーカープロセスは、タスクを実行する前に一度だけ、simulation.jaxPlatforms、simulation.jaxPreallocate、simulation.jaxMemoryFraction によってJAXを設定し（JAX/Flax ランナー を参照）、その後 _get_worker_initializer() が返すワーカーの初期化関数（例えば上記の load_model）を呼び出します。ワーカープロセスがGPUを共有できるよう、GPUメモリの事前確保はデフォルトで無効になっています。メインプロセスは設定されないため、エージェントがメインプロセスで作成されるときにGPU上でJAXを使う場合は、環境変数でも XLA_PYTHON_CLIENT_PREALLOCATE=false を設定してください。

  • ワーカープロセスはシミュレーションの間存続するため、jax.jit() でコンパイルされる関数は、最初の呼び出し時にワーカープロセスごとに一度だけコンパイルされ、以降のステップで再利用されます。コンパイルされた関数はpickle化できないため、エージェントの属性として保持するのではなく、モジュールのトップレベルで定義してください。

  • エージェントが保持するjax配列、Flaxのモジュールとパラメータは、タスクごとにpickle化され（並列ランナー を参照）、ワーカープロセスのデフォルトデバイスにコピーされます。大きなモデルや読み取り専用のモデルは、代わりにワーカーの初期化関数でワーカープロセスごとに一度だけ読み込んでください。

  • メインスクリプトなど、ワーカープロセスがインポートするモジュールのトップレベルでJAXを実行しないでください（例えばjax配列を作成しないでください）。また、ワーカーの初期化関数にjax配列を渡さないでください。そうしないと、JAXが設定される前に初期化されてしまいます。

  • 結果が pams.runners.SequentialRunner と同じになるよう、jax.random の鍵を含む乱数は agent.prng から導出してください。

# my_agent.py, which the worker processes can import
import flax.linen as nn
import jax
import jax.numpy as jnp

from pams.agents import Agent


class Model(nn.Module):
    @nn.compact
    def __call__(self, x):
        return nn.Dense(1)(x)


@jax.jit
def predict(params, x):  # compiled once per worker process
    return Model().apply(params, x)


class MyFlaxAgent(Agent):
    def setup(self, settings, accessible_markets_ids, *args, **kwargs):
        super().setup(settings, accessible_markets_ids, *args, **kwargs)
        key = jax.random.PRNGKey(self.prng.randrange(2**31))
        self.params = Model().init(key, jnp.zeros((3,)))  # pickled in every task

    def submit_orders(self, markets):
        ...  # e.g., predict(self.params, features)

# main.py
import random

from my_agent import MyFlaxAgent
from pams.runners import JaxAgentParallelRunner

if __name__ == "__main__":
    runner = JaxAgentParallelRunner(settings=config, prng=random.Random(42))
    runner.class_register(MyFlaxAgent)
    runner.main()

TensorFlow ランナー¶

pams.runners.TensorFlowAgentParallelRunner は、submit_orders で TensorFlow を使うエージェント（例えば Keras のモデル）のための実験的な pams.runners.MultiProcessAgentParallelRunner です。TensorFlow は pams の依存パッケージではないため、別途インストールしてください（例えば pip install tensorflow、CPU 専用版であれば pip install tensorflow-cpu）。import pams は TensorFlow をインポートせず、TensorFlow がインストールされていない状態でこのランナーを作成すると ImportError が送出されます。

  • TensorFlow は fork セーフでないため、ワーカープロセスはデフォルトで spawn によって起動されます（default_start_method = "spawn"）。メインプロセスで一度 TensorFlow が実行されると（例えばエージェントのモデルを構築するためや、先に実行した pams.runners.SequentialRunner の中で）、fork で起動されたワーカープロセスはそのメモリのコピーを持ちますが、スレッドは持ちません。そのため、そこでは TensorFlow の演算がハングすることがあり、GPU は使えず、TensorFlow を設定することもできません。

  • 各ワーカープロセスは、タスクを実行する前に一度だけ、simulation.tensorflowIntraOpThreads、simulation.tensorflowInterOpThreads、simulation.tensorflowGpuMemoryGrowth で TensorFlow を設定し（TensorFlow ランナー を参照）、その後、_get_worker_initializer() で与えられるワーカーの初期化関数（例えば上記の load_model）を呼び出します。デフォルトでは、CPU は同時に動くワーカープロセスの間で分割され、ワーカープロセスが GPU を共有できるよう GPU のメモリ増加（memory growth）が有効になります。メインプロセスは設定されません。各ワーカープロセスに専用の GPU を割り当てるには、初期化関数の中で tf.config.set_visible_devices を呼び出してください。メモリ増加を有効にするために GPU がすでに列挙されているため、デフォルトでは、そこで設定した CUDA_VISIBLE_DEVICES は効果がありません。

  • エージェントはタスクごとに pickle 化されます（並列ランナー を参照）。tf.Tensor と tf.Variable はその値のコピーとして pickle 化され、Keras 3 のモデルは .keras 形式で保存することで pickle 化されます（小さなモデルでも数十ミリ秒かかります）。また、tf.function で作られた関数は pickle 化できません。そのため、エージェントにはモデルのキー（例えばそのパス）を保持させ、以下のようにモジュールのトップレベルにあるキャッシュからモデルを取得してください。こうすることで、各ワーカープロセスはモデルを一度だけ読み込み、以降のステップで再利用します。

  • モジュールのトップレベルで TensorFlow をインポートすることは問題ありませんが、メインスクリプトなど、ワーカープロセスがインポートするモジュールのトップレベルで TensorFlow を実行（例えばテンソルやモデルを作成）しないでください。そうしないと、TensorFlow が設定される前に初期化され、シミュレーションは失敗します。

  • 結果が pams.runners.SequentialRunner と同じになるよう、乱数（例えば tf.random.stateless_normal のシード）は agent.prng から導出してください。ワーカープロセス上の TensorFlow の乱数状態はメインプロセスに返されません。

  • CPU では、長い軸に沿ったリダクションや行列積などの大きな演算の結果は、tf.config.experimental.enable_op_determinism() を使っても、intra-op スレッド数によって変わります。ワーカープロセスでのデフォルトのスレッド数は、TensorFlow がすべての CPU を使うメインプロセスとは異なることがあり、numParallel と maxNormalOrders によっても変わります。pams.runners.SequentialRunner と同一の結果を得るには、simulation.tensorflowIntraOpThreads を設定し、pams.runners.SequentialRunner を実行するプロセスでも、TensorFlow が実行される前に tf.config.threading.set_intra_op_parallelism_threads で同じ数を設定してください。

  • このランナーが pams.runners.SequentialRunner より速くなるのは、エージェントの TensorFlow の計算が、タスクごとのシミュレーションのコピーよりもはるかに重い場合に限られます。また、TensorFlow をインポートする各ワーカープロセスの起動にも数秒かかります。

# my_agent.py, which the worker processes can import
import functools

import tensorflow as tf

from pams.agents import Agent


@functools.lru_cache(maxsize=None)
def get_model(path):  # loaded once per process
    return tf.keras.models.load_model(path)


class MyKerasAgent(Agent):
    def setup(self, settings, accessible_markets_ids, *args, **kwargs):
        super().setup(settings, accessible_markets_ids, *args, **kwargs)
        self.model_path = settings["modelPath"]  # only the path is pickled

    def submit_orders(self, markets):
        model = get_model(self.model_path)
        ...  # e.g., model(features, training=False)

# main.py
import random

from my_agent import MyKerasAgent
from pams.runners import TensorFlowAgentParallelRunner

if __name__ == "__main__":
    runner = TensorFlowAgentParallelRunner(
        settings=setting_dict_or_json, prng=random.Random(42)
    )
    runner.class_register(MyKerasAgent)
    runner.main()

PyTorchを使うエージェント¶

pams.runners.TorchAgentParallelRunner （実験的機能）は、submit_orders で PyTorch を使うエージェントのための pams.runners.MultiProcessAgentParallelRunner のサブクラスです。PyTorchはpamsの依存パッケージではないため、pip install torch などにより各自でインストールしてください（お使いのプラットフォームとアクセラレーター向けのビルドについては、PyTorchのWebサイトを参照してください）。pamsがPyTorchをインポートするのはこのランナーが作成されたときのみで、PyTorchがインストールされていない場合、ランナーは ImportError を送出します。このランナーは、プロセスランナーの機能に加えて、以下を行います：

  • simulation.startMethod が設定されていない場合、ワーカープロセスを spawn で起動します。PyTorchでは fork は安全ではないためです。forkされたプロセスではCUDAを初期化できず、また、PyTorchがスレッドプールを実行している間にforkされたプロセスはデッドロックすることがあります。spawn を使うため、Linuxを含むすべてのプラットフォームで、ランナーを実行するコードは if __name__ == "__main__": の下に置く必要があり、ユーザー定義クラスはインポート可能な .py ファイルに記述する必要があります（並列ランナー を参照）。

  • ワーカー全体のスレッド数がCPUの数を超えないよう、各ワーカープロセスでのPyTorchのスレッド数を simulation.torchNumThreads に設定します（デフォルト：メインプロセスでのPyTorchのスレッド数を、numParallel とセッションの maxNormalOrders の最大値のうち小さい方で割った値、ただし最小1）。小さなモデルでは、多くの場合1が最も高速です。

  • メインプロセスとワーカープロセスで、torch.multiprocessing の共有戦略を file_system に設定します。メインプロセスでの設定はプロセス全体に影響します。サブクラスは、クラス属性 torch_sharing_strategy を None に設定することで、現在の戦略を維持できます。

モデルのパラメータなど、エージェントが保持するテンソルは、共有メモリを通じてワーカープロセスに送られます。テンソルは最初のタスクで共有メモリに移され、以降のタスクではテンソルのデータの代わりに、テンソルごとに数百バイトのハンドルが送られます。以下の点に注意してください。

  • それでも各タスクはすべてのエージェントのすべてのテンソルを参照し、それらを開くのには時間がかかるため、タスクのコストはテンソルの数とともに増加します。例えば、それぞれ6個のテンソルからなるモデルを持つ50体のエージェントでは数十ミリ秒かかります。このランナーが pams.runners.SequentialRunner より高速になるのは submit_orders にそれよりもはるかに長い時間がかかる場合に限られるため、お使いのエージェントで計測してください。

  • Linuxでは共有メモリは /dev/shm にあり、すべてのエージェントのテンソルを格納できる大きさが必要です。Dockerのデフォルトは64 MBで、--shm-size で増やせます。

  • ワーカープロセスはメインプロセスと同じメモリを参照するため、submit_orders 内での（学習などによる）テンソルのインプレースの変更は、メインプロセス上のテンソルを変更します。一方、ワーカープロセス上でのエージェントのその他の変更は失われます。submit_orders ではテンソルを読み取り専用にしてください。

  • ワーカープロセスから戻ってくるのは、各エージェントの prng の状態のみです。PyTorchの乱数は、PyTorchのグローバルな生成器ではなく、torch.Generator().manual_seed(self.prng.randrange(2**32)) のように prng でシードを設定した生成器から生成してください。

  • 行列積など、PyTorchの一部の演算の結果は、スレッド数やデバイスによって丸め誤差が異なることがあり、そのような違いがシミュレーションの展開を変えることがあります。結果を比較するには、pams.runners.SequentialRunner を torch.set_num_threads(n) の後に実行し、torchNumThreads を n に設定してください。

このランナーはデバイスを選択しません。ワーカープロセスはメインプロセスと同じデバイスを参照し、CUDAを使う各ワーカープロセスはそれぞれ独自のCUDAコンテキストを作成します。これはGPUメモリを数百MB消費します。CUDAのテンソルはWindowsがサポートしていないCUDA IPCで送られることになるため、エージェントが保持するテンソルはCPU上に置いてください。各タスクはエージェントの新しいコピーを受け取るため、submit_orders 内でテンソルをデバイスに移すと、タスクごとにコピーが発生します。モデルをワーカープロセスごとに一度だけデバイスにコピーするには、以下のランナーのように、ワーカーの初期化関数でモジュールレベルの変数にモデルを読み込み、submit_orders ではその変数を使ってください。ワーカーの初期化関数をオーバーライドするサブクラスも、このランナーの引数で _initialize_torch_worker を呼び出す必要があります。

# my_torch_runner.py, which the worker processes can import
from typing import Any, Callable, Optional, Tuple

import torch

from pams.runners import TorchAgentParallelRunner
from pams.runners.torch_parallel import _initialize_torch_worker

MODEL = None


def initialize_worker(path: str, *args: Any) -> None:
    global MODEL
    _initialize_torch_worker(*args)
    device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
    MODEL = ...  # load the model from path and move it to device


class MyTorchRunner(TorchAgentParallelRunner):
    def _get_worker_initializer(self) -> Optional[Callable[..., Any]]:
        return initialize_worker

    def _get_worker_initargs(self) -> Tuple[Any, ...]:
        return ("model.pt",) + super()._get_worker_initargs()
